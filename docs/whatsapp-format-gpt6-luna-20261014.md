# WhatsApp format and Zuvel GPT-6 Luna change

Daniel approved this bounded design: normalize surplus formatting markers at
the WhatsApp send boundary while preserving bullets and native bold; enable
GPT-6 Luna for Zuvel with the existing OpenAI credential and low reasoning;
test before activation and retain recovery. No new API key, Meta token,
connection, WABA or phone registration is in scope.

## Root cause and changes

The screenshot response at 2026-10-14 16:15:14 UTC was generated by published
version `01a13b27-29d7-731e-b1c9-8b3c5ef9e638`. The stored model output contained
two double-asterisk delimiters; the send payload was identical and DELIVERED.
Other replies from the same version used correct single asterisks. This proves
the prompt rule is nondeterministic, not that the previous publication failed.

AI text is normalized during preparation and again transactionally at claim,
covering pre-release pending payloads. The persisted channel payload matches the
body sent; the original model output stays in messages for audit. Native bold
and bullet characters are retained; multi-asterisk runs become single pairs and
orphan markers are dropped. Templates, identity resolution, dispatch fences,
human authority and already-delivered idempotency remain unchanged. This is a
targeted AI-to-WhatsApp formatter, not a general Markdown renderer.

The closed model allowlist now supports GPT-5.6 Luna and GPT-6 Luna with low
reasoning. Existing defaults remain 5.6. A saved per-agent model choice reaches
the compiled spec and real SDK Agent; changing it changes the spec digest.

Ruling: code provenance changes would otherwise stop the published account
before a new reviewed candidate is ready. A server-owned explicit mapping of
previously reviewed version UUID to its exact old code digest permits runtime
selection and rollback of those specific compatible versions. Empty by default;
missing current digest, wrong version, wrong digest and unreviewed/unpublished
rollback remain rejected. New candidate publication still requires current-code,
current-revision reviewed evidence; compatibility never bypasses that gate.
Cost if wrong: a release operator could certify incompatible prior behavior;
activation must list only verified prior Zuvel versions and preserve fail-closed
behavior for every other version.
